# 成熟库评估：为什么换了两项，留下三项

最初只读代码时，我们判断五项手写实现都能换成成熟库。随后把正常输入、坏格式和并发场景交给两种实现，逐项核对结果，探针推翻了其中三项。选型需要可复现的对比，不能只看库的 README 和接口签名。

这里的“探针”是替换前的临时对照程序，用同一份输入观察旧代码与候选库。“契约测试”则长期留在仓库，固定项目必须保持的行为。探针回答库是否适合，契约测试防止后续修改破坏已经作出的决定。

下文的 CI 是提交后在 GitHub Actions 上自动运行的检查流程；Mock 使用固定假回复，验证程序流程时不需要调用真实模型。

这次最重要的原则是：**证据和账本宁可报错，也不能让库自己凑一个数。** 监控缺值变成 0，会让诊断误把数据缺失当成系统正常；服务商返回的小数 token 被截成整数，会让费用账本失真。减少代码要以保住这些含义为前提。

| 项目 | 评估版本 | 最终选择 | 保留的项目责任 |
|---|---|---|---|
| Prometheus 查询 | client_golang v1.25.0 | 保留薄适配器 | 严格采样点、访问范围、响应上限与错误脱敏 |
| 工具参数和报告校验 | jsonschema-go v0.4.3 | 替换两套字段校验 | 原始输入边界、公开 Schema 字节、报告数字与真实步骤 |
| 导入方向检查 | golangci-lint v2.15.0 的 depguard | 替换通用导入检查 | 项目规则配置；archcheck 留下三类专有检查 |
| MySQL 迁移 | golang-migrate v4.20.1 | 保留 Apply | 同会话锁、取消、历史校验和失败后的继续执行 |
| 模型客户端 | openai-go/v3 v3.97.0 | 保留客户端及回复类型 | 严格用量、每次尝试的预算、完整审计与 HTTP 边界 |

“保留”描述的是本次受测版本与项目约束之间的取舍。以后接口范围扩大或库修正行为时，可以拿同一组契约重新评估。

## 1. Prometheus：数据缺失不能变成零

### 原来解决什么问题

医生需要问“最近错误率是多少”，工具层不应该知道 Prometheus 的 JSON 外形。原来的[客户端](../../internal/doctor/source/prometheus/client.go)把 vector、matrix、scalar、string 结果整理成统一采样点，再把告警整理成统一结构。接口范围固定，HTTP 访问已经由共用的 `httpbackend` 处理，因此实现的是一层较小的格式适配。

候选是 client_golang 的查询 API。它可以接手查询请求、回复解码和类型定义；它是否能完成查询之外，还要检查坏数据会被怎样处理。

### 探针差异与决定

| 输入或条件 | 原实现 | client_golang v1.25.0 | 决定 |
|---|---|---|---|
| 采样点只有时间戳 `[100]` | 拒绝不完整采样点 | 缺失数值留下零值 0 | 保留原解析边界 |
| `resultType: string` | 返回字符串采样点 | 返回不支持该类型的错误 | 保留现有能力 |
| `status` 是未知值 | 拒绝 | 未按错误状态拒绝 | 固定为拒绝契约 |
| 查询方法、读入上限、错误文本 | 共用 GET、2 MiB 上限、错误不带后端地址 | 默认先用 POST、读入无上限、错误可能带地址 | 替换需要额外适配 |

这里的 0 会被当成诊断证据。为了在库前识别缺值，仍然得自己解析采样点，原本要删除的工作又回来了。只删掉解码函数还会丢掉字符串结果，因而本项保留手写。

### 仍然由项目负责什么

工具的时间范围、步长与结果数量限制仍由项目控制。Prometheus 与 Loki、Jaeger 等数据源共用的 HTTP 边界也继续保留：固定目标、只读访问、禁止重定向、有界读入和错误脱敏。它们决定了医生能看哪里、一次能读取多少数据。

复核入口是 [TestQueries](../../internal/doctor/source/prometheus/client_test.go)：短采样点用例已有，后来补上未知状态和字符串结果。没有引入查询 API；仓库原有 client_golang 的指标采集用途不受影响。

### 三个面试追问

1. **为什么不用官方客户端？** 官方客户端覆盖的用途更广，但本次版本对缺值的解释不满足证据契约。预解析、大小限制和错误脱敏都补回后，适配成本抵消了收益。
2. **为什么不把缺值按 0 处理，先让诊断跑完？** 0 是有效观测值，缺值是观测失败。二者会使 Agent 得出不同判断，应把失败交给诊断流程处理。
3. **怎样证明保留不是凭偏好？** 同一输入得到了不同结果，复核又确认了库的解码行为；现在的测试固定了拒绝缺值、拒绝未知状态和支持字符串结果。

## 2. JSON Schema：让库判断格式，让项目保住原数据

### 原来解决什么问题

JSON Schema 是一份数据格式说明，例如某字段必须是整数、范围为 0–3600。项目原来分别为工具参数和最终报告写了类型、必填、枚举、长度与范围检查。两处都从有限字段起步，随后出现了重复的通用校验逻辑。

这次把字段规则交给 jsonschema-go v0.4.3。`Resolve` 把声明整理成可复用的校验器，`Validate` 检查一次输入，`ApplyDefaults` 补上工具定义允许的默认值。工具在菜单构建时解析规则；报告按组件表缓存，同一组件表的并发首次调用也只解析一次。

### 为什么模型声明和校验规则要分开

模型看见的 Schema 也是提示词的一部分。替换前先保存 golden 文件，也就是一份作为比较基准的原始输出；测试直接比较字节，不先解析成对象。这样换库不会顺手改动模型看到的字段顺序或数字写法。

报告的校验规则可以从原声明 JSON 构造，工具规则则必须直接读结构体字段。工具的 `Minimum` 为 0 时，原有 `omitempty` 会让它从公开 JSON 中消失；如果拿这份 JSON 重建校验器，原本要拒绝的 `-1` 就可能通过。现在保留旧公开字节，同时在校验规则中明确设置零下界。

### 探针差异与对策

| 输入或条件 | 旧校验路径 | 候选库路径 | 最终处理 |
|---|---|---|---|
| 工具整数写成 `3.0`、`1e3` | 拒绝 | 接受 | 经审核接受，转换为 int 后分别为 3、1000 |
| `3.0000000000000001`、`3600.0000000000001`、`1e-1000` | 拒绝 | float64 解码后为 3、3600、0 | 经审核接受；实际使用值必须在范围内 |
| 报告引用真实步骤 `1.0`、`1e0` | 格式检查通过，读取失败后误按步骤 0 拒绝 | 能读取为步骤 1 | 修复旧读取错误，仍查步骤是否真实存在 |
| 报告自由参数为 `9007199254740993` 或 `1e-1000` | 输出保留原数字 | 若重编码 float64，会变为 `9007199254740992` 或 0 | 输出改用保留数字文字的树 |
| `confidence=1.0000000000000001` | 按 float64 判断，但输出保留原数 | 校验通过，重编码会变成 1 | 校验与输出分开 |
| 报告自由参数 `1e309` | 可以保留并输出 | float64 解码溢出 | 经审核新增拒绝，提示数字超出范围 |
| 重复键、过深嵌套、超大输入、虚构步骤 | 项目拒绝 | 单靠字段校验覆盖不了 | 项目继续检查 |
| Schema 没有 `$schema` 字段 | 可用 | 17 份工具规则和报告规则均能 Resolve、Validate | 保持原声明 |

float64 是 Go 的双精度浮点数，能表示的精度和数量级有限。上述舍入发生在 JSON 解码时；不是库拿到精确数字后故意改它。这里接受的是经审核的工具输入行为，不能据此把服务商账单中的错误类型也转换成合法用量。

### 仍然由项目负责什么

报告最多 16 KiB，同一份输入解码两次：第一次用 [jsonstrict](../../internal/platform/jsonstrict/doc.go) 检查重复键和十六层嵌套，并把数字保存成 `json.Number`，即原来的数字文字；第二次解成 float64，只供库校验和读取证据步骤。最终输出只来自第一棵数据树，因此校验不会改写报告中的数字。

工具的 8192 字节上限、非法 UTF-8 拒绝，以及报告的真实步骤检查仍属于项目边界。报告延续旧的非法 UTF-8 替换行为。jsonstrict 还拒绝尾随第二份 JSON；格式错误保留标准库给出的具体原因，便于模型修正输入。

阅读 [工具规则](../../internal/doctor/tools/schema.go)、[报告规则缓存](../../internal/doctor/agent/schema.go)和[报告校验](../../internal/doctor/agent/report.go)，再看[工具 golden](../../internal/doctor/tools/schema_golden_test.go)、[报告 golden](../../internal/doctor/agent/schema_golden_test.go)与[报告输出测试](../../internal/doctor/agent/report_test.go)。错误提示换成带路径的库错误，这是非法调用时模型会看见的行为变化。

### 三个面试追问

1. **为什么不是把旧 Schema JSON 全部转成库类型？** 工具的公开 JSON 会省略零下界，结构体却保留着这条规则；直接转换会漏掉负数检查。
2. **为什么要解码两次？** 库把 `json.Number` 当成字符串，直接交给它会校验失败；全程使用 float64 又会改写输出。两份树分别承担校验与输出，职责明确。
3. **怎样证明模型输入没有变？** 在替换前单独提交 golden，之后逐字节比较全部工具定义及固定组件表的报告定义。它证明声明未变；错误提示和部分数字接受规则另有测试与记录。

## 3. depguard：通用扫描交给工具，项目规则留在配置

### 原来解决什么问题

一个 Go 模块里的代码仍能互相导入。医生一旦直接依赖靶场或注入器，就可能绕过外部观测，得到实验答案。原来的 archcheck 同时扫描导入路径、检查文件角色、目录位置、标准答案读取和 Compose 配置，集中挡住这些边界破坏。

导入规则是通用静态检查，适合交给 depguard。它运行在固定版本 golangci-lint v2.15.0 中，按文件匹配规则，再检查禁止导入的包。本项目在 golangci-lint 中只启用这一个检查器；staticcheck 继续独立运行。

### 迁移哪些规则

| 配置规则 | 检查对象 | 要保护的边界 |
|---|---|---|
| `doctor-boundary` | 医生代码 | 不导入靶场、注入器、评测器、压测器或 os/exec |
| `shop-boundary` | 靶场代码 | 不依赖医生、注入器或评测器完成业务 |
| `platform-boundary` | 通用基础设施 | 显式禁止 internal 下五个业务目录及 gen |
| `domain-files` | 非 platform 的 model.go、service.go | 业务规则不直接绑定 HTTP、RPC、SQL、Redis、Kafka |
| `shop-storage-files` | 靶场仓储、缓存、消息文件 | 不承担 Gin 或 gRPC 接口职责 |
| `shop-interface-files` | 靶场 HTTP/gRPC 适配文件 | 不越过业务层直接使用 database/sql |
| `shop-client-files` | 靶场客户端文件 | 不引入服务端 Gin 请求处理 |

七条规则分别临时加入违规导入，新旧检查都拒绝；验证后撤销了临时改动。包名采用精确匹配加子包前缀，避免把名字相似的目录误判成受限包。完整配置在 [.golangci.yml](../../.golangci.yml)。

### 行为差异与仍然手写的部分

| 输入或条件 | 旧 archcheck | depguard | 对策 |
|---|---|---|---|
| 七类违规导入 | 拒绝 | 对当前构建拒绝 | 把对应扫描和测试移除，规则迁入配置 |
| 只在 `leakbug` 构建中的违规 | 扫描到文件即可拒绝 | 默认构建看不到 | CI 和本机都增加 `--build-tags=leakbug` |
| 违规文件带生成标记 | 仍检查 | 可由配置决定是否跳过 | 禁止跳过生成标记，保留边界 |
| 目录布局、标准答案访问、Compose 挂载及内部端口 | 检查 | 不属于导入检查 | 继续由 archcheck 负责 |

替换删除的是通用导入遍历，留下的是项目规则和无法用导入路径表达的检查。depguard 不能证明数据库账号只读，账号权限仍需真实集成测试验证。

### 三个面试追问

1. **为什么不把 archcheck 整个删掉？** 禁止读取场景答案和限制 Compose 挂载不是导入规则。把这些检查留下，比勉强套进另一套配置更直接。
2. **为什么同一个检查器要跑两次？** `leakbug` 会选择另一份源码，默认构建不会分析它。一次通过只证明当前构建的导入合法。
3. **为什么配置行数可能比原代码多？** 声明式规则重复列出包名，但不再需要项目维护源码导入扫描。要比较维护责任，而不是只比较文本总行数。

## 4. 数据库迁移：成功执行文件之外，还有启动与恢复契约

### 原来解决什么问题

两个服务同时启动时，不能重复执行建表和改表文件。原来的 [Apply](../../internal/platform/migrate/migrate.go)在同一 MySQL 连接上拿命名锁，核对文件校验和，按顺序执行，再记录成功历史。命名锁属于数据库会话，因此拿锁、执行、解锁必须使用同一连接。

golang-migrate 能接管版本记录和顺序执行。探针用 `WithConnection` 复用连接设置，保持多语句关闭；只在内存文件系统中提供它需要的 `.up.sql` 文件名，没有改生产迁移文件。实际是 doctor 42 个 SQL 加 shop 5 个 SQL，共 47 个；最初的 43 个 doctor 文件把 README 也数了进去。

库会用 dirty 标记一次迁移尚未成功完成。留下这个状态后，下次启动先报错，要求操作者核对数据库实际执行到哪里，再处理版本状态。

### 探针差异与决定

| 输入或条件 | 旧 Apply | golang-migrate v4.20.1 | 影响 |
|---|---|---|---|
| 空库执行全部 47 个 SQL | 成功，重复调用成功 | 成功，重复调用 ErrNoChange | 核心执行能力满足要求 |
| 直接复用旧历史表 | 正常读取 | Up 因缺 dirty 列报 MySQL 1054 | 同名表结构不同，需要接管路径 |
| 新表 schema_version 为空时条件插入旧版本 | 无需接管 | 首次插入 1 行，重复插入 0 行 | 单次接管可行，迟到调用不会回退版本 |
| 两个调用并发接管并推进 | 都成功 | 10 轮中 5 轮一方报 1213 死锁 | 最终版本正确也不能算两个调用都成功 |
| 另一连接持锁 12 秒 | 等待后成功 | 约 10 秒报 ErrLocked，重试后成功；构造阶段也会发生 | 还要保留自己的锁策略 |
| 错误 SQL 修正后重新执行 | 继续未完成迁移 | dirty=true，继续报 ErrDirty | 恢复需要额外人工流程 |
| SQL 执行中取消 ctx | 停止，后续 INSERT 未执行 | 仅取消构造时的 ctx 不能停止 Up | 丢失取消契约 |
| 取消时桥接 GracefulStop | 无需桥接 | 等当前 SQL 后停，但 -race 报库内竞态 | 候选桥接不可接受 |
| 已执行文件被改写 | 校验和不符，拒绝 | ErrNoChange，未报告改写 | 丢失运行时历史核对 |

这次要替换的顺序执行只占迁移器的一部分。补回同会话锁、释放结果检查、取消和校验和，再长期维护旧库接管，所需代码接近原实现，还引入了新的恢复状态，所以决定保留。

### 并发接管为什么会死锁

条件插入的意思是“只有新版本表为空，才写入旧库的最高版本”。它防止较晚到达的启动者把已经前进的版本写回去，但单条 SQL 并不等于没有锁竞争。

这里依据探针 SQL 和 InnoDB 在 REPEATABLE READ 下的规则解释锁循环；CI 实测记录了 1213，但没有用 `SHOW ENGINE INNODB STATUS` 保存死锁图，因此不是对当次每一把锁的直接观测。

间隙锁保护索引记录之间的空位，防止其他事务插入。空表也有索引末尾的边界，称为 supremum。`INSERT … SELECT … WHERE NOT EXISTS` 读取这个范围时可能取得共享的间隙锁；真正插入前还需要插入意向锁，表示准备占用这个空位。参见 [InnoDB SQL 加锁规则](https://dev.mysql.com/doc/refman/8.4/en/innodb-locks-set.html)和[间隙锁、插入意向锁](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html)。

| 时序 | 启动者 A | 启动者 B |
|---|---|---|
| 1 | 读到空表，取得保护空位的锁 | 也读到空表；间隙锁之间可以共存 |
| 2 | 准备插入，等待 B 的间隙锁释放 | 准备插入，等待 A 的间隙锁释放 |
| 3 | 两者互相等待 | InnoDB 选择其中一个回滚，返回 1213 |

这是候选接管 SQL 的并发问题。要采用它，就需要把接管串行化或设计有界重试，不能把死锁当成“另一方已经成功”而吞掉。本次保留 Apply，因此没有把这条接管路径放进生产代码。

### CI 为什么会假绿

当时的 Bash 步骤用 `go test … | tee 日志文件` 同时显示和保存日志。默认管道退出码取最后一个命令：测试失败了，`tee` 仍可能写日志成功并返回 0，`bash -e` 就不会因为前面的失败退出。后面的 Python 又只检查“有 pass、没有 skip”，漏掉了 fail。

现在 [.github/workflows/ci.yml](../../.github/workflows/ci.yml)先开启 `set -o pipefail`，让管道中的失败传出来；事件检查还拒绝 `fail` 和 `build-fail`，包括没有 Test 字段的包级失败。这样测试进程和结果事件两条路径都能挡住失败。

修门禁时刻意保留库内竞态：[CI #75](https://github.com/Li-Nepenthe/opsdoctor/actions/runs/42756064473)按预期在集成步骤变红，唯一失败子用例是 `library_graceful`。撤掉探针并补原实现契约后，[CI #76](https://github.com/Li-Nepenthe/opsdoctor/actions/runs/42757557487)才全绿，集成事件 pass=75、fail=0、skip=0。pass 包含父测试和子测试，不能把它当成 75 个独立功能。

### 仍然由项目负责什么

当前迁移器保留命名锁、取消传播、执行历史及校验和核对。释放锁失败时丢弃物理连接，避免把可能还持锁的会话放回连接池。[恢复契约测试](../../internal/platform/migrate/migrate_integration_test.go)分别覆盖执行中取消和错误 SQL 修正后继续，并验证成功历史与实际写入。

这里测试的是确定未成功的迁移修正后重试。MySQL 的 DDL 不是整批事务，执行成功但记历史前断电仍需要核对数据库实际状态；保留手写没有消除这类恢复成本。

### 三个面试追问

1. **条件插入不是一条 SQL 吗，为什么还会死锁？** 原子性不消除内部加锁。两个事务都先保护空范围，再等待对方释放以便插入，就可能形成锁等待环。
2. **为什么不直接 Force 到旧版本？** 迟到的接管者可能把另一实例已经推进的版本覆盖回去。条件插入避免了这个回退，但还需要解决并发死锁。
3. **CI 页面全绿，为什么还要读日志？** 第 4 项证明门禁本身也会漏错。先让已知失败确实变红，再核对 pass/fail/skip，才能知道通过意味着什么。

## 5. OpenAI 客户端：类型方便不能替代严格计费

### 原来解决什么问题

模型调用除了发 HTTP，还要在每次尝试前预留费用、保存脱敏请求和回复、按状态决定能否重试，并让恢复流程读懂历史回复。当前只使用 Chat Completions 与 Responses 两种接口的少数字段，因此原来把协议转换集中在[客户端包](../../internal/doctor/llm/openai/doc.go)。

官方 openai-go/v3 v3.97.0 可以提供请求类型、URL 拼接和响应类型。探针已确认原始请求与回复能同时拿到，工具 parameters 可通过额外字段保留字节，附加客户端说明头可以移除；`WithMaxRetries(0)` 遇到先 429 后 200 的模拟服务器也只发一次请求。真正决定取舍的是回复边界，而不是 SDK 做不到发送请求。

### 探针差异与决定

| 输入或条件 | 原实现 | SDK 候选 | 决定 |
|---|---|---|---|
| Chat token 为字符串或小数；content/arguments 为对象；Responses token 为字符串、arguments 为对象，共 6 种 | 全部拒绝 | 全部接受，发生数字或字符串转换 | 保留严格解码，也不改成只用 SDK 类型 |
| 状态 201、204，或未跟随的 3xx | 报错 | 不返回错误 | 保留只接受 200 的策略 |
| 错误 JSON 外层有 request_id | 保存完整脱敏 JSON | Error.RawJSON 只含内层 error | 完整审计仍需自行处理 |
| 502 的 error 字段为字符串 | 按 502 分类 | 可能返回解码类型错误，不能只按 API 错误类型分类 | 保留项目的状态码判断 |
| 回复恰好 1 MiB / 多 1 字节 | 前者接受，后者拒绝且不重试 | 默认都读入 | 保留读入上限 |
| 同源重定向 | 不跟随，目标收到 0 次 | 默认跟随；禁跟随后仍需检查 3xx | 保留重定向策略 |
| Chat/Responses 固定请求，含工具往返 | 原有字节 | 适配后语义一致，字段顺序不同 | 不能宣称字节相同 |
| 阶段 9 P9-53 的真实 DeepSeek 保存回复 | 正常解码 | 正常解码，结果一致 | 留作原实现回归样本 |

token 进入账本后会乘以单价。把 `"20"` 转成 20，或者把 `20.5` 截成 20，掩盖的是上游协议错误。它与 Prometheus 把缺值补成零是同一类问题：**证据和账本宁可报错，也不能让库自己凑一个数。** SDK 类型内含宽松解码，因此只换类型同样会引入差异。

### 仍然由项目负责什么

每次尝试前预留预算、完整脱敏审计、重试分类、总截止时间、收到响应后的网络失败处理，以及大小和重定向策略仍由项目掌握。SDK 内部重试必须关闭，否则一次外部调用里的重试可能绕过下一次费用预留。

探针时三个生产文件共 476 行，估算可删 160–180 行、需要新增 240–300 行，净增 60–140 行。这是原型与函数边界支持的替换估算，生产替换并未实施。加上尚未找到真实 OpenAI Responses 历史样本，本项触发停止条件，保留现有实现。

真实 DeepSeek 样本来自[阶段 9 P9-53 的脱敏数据库导出](../reports/phase-09-pilot2-judge-response.log)，不是本次重新调用服务取得。它的输入为 13808、输出为 466、缓存命中为 768、未命中为 13040。原件逐字节复制到 testdata，固定 SHA-256；工具参数里的非法 JSON 字符串原样保留，让下一层处理格式错误，传输层不擅自修复。

新增的[保存回复测试](../../internal/doctor/llm/openai/responses_test.go)和[HTTP 边界测试](../../internal/doctor/llm/openai/client_test.go)已经通过复核。复核者又临时做了“去掉禁止重定向”“上限放宽 1 字节”两次变异，两次都被新测试抓住；这些故意破坏未保留。[CI #77](https://github.com/Li-Nepenthe/opsdoctor/actions/runs/42780936018)在 `92e94b2` 上全绿，集成 pass=75、fail=0、skip=0。

### 三个面试追问

1. **用了 SDK 为什么还需要自己重试？** 项目要求每一次尝试先预留预算，并区分是否收到响应。SDK 内部重试不掌握这些账本状态。
2. **只用 SDK 的类型，HTTP 仍自己写，行不行？** 本次版本的宽松转换就在类型解码中。只换类型仍会把错误用量变成合法数字，因此也未采用。
3. **凭一份历史样本能证明兼容所有服务商吗？** 它只证明这份 DeepSeek 保存回复的回归。Responses 目前用构造样本覆盖协议，缺少真实历史样本是本次保留实现的一项依据。

## 怎样对照代码学习

先读每项的差异表，再定位上面的契约测试，观察输入为什么被接受或拒绝。要验证通用导入规则，按[阶段 0 实验二](phase-00-foundation.md#实验二让依赖检查报错)临时制造一次违规，完成后撤销。

本次没有重跑付费评测。简历和台账里的评测数字来自替换前的代码；本次替换前 main 为 `16db4e8`。Schema golden 只证明模型声明字节未变，本地测试与 CI 证明受测契约通过，不能把它们写成替换后的真实模型效果或费用实测。版本与口径汇总见[设计记录](../decisions.md)。
