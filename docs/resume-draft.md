# 简历项目描述与指标口径

这份项目文案不含个人联系方式。四条分别突出 Agent 取证、评测、恢复与安全、后端优化；具体实验条件留在下面，便于面试时沿原始记录解释。

## 项目描述

**OpsDoctor：大模型驱动的 Go 故障诊断 Agent**

技术栈：Go、Gin、gRPC、MySQL、Redis、Kafka、LLM、RAG、MCP、OpenTelemetry。

构建电商故障靶场与可独立部署的诊断服务，贯通告警、自动取证、证据报告和人工审批修复。

- **Agent 取证：**基于 Function Calling 实现多轮诊断，接入指标、调用链、日志和执行计划等 **16 个只读工具**；校验参数与证据引用，通过 SSE 展示步骤、MCP 开放工具。同批次平均诊断 **20.4 秒**，模型调用账本均费约 **$0.025**。
- **评测与消融：**覆盖 13 类故障与对照场景，比较完整工具、RAG 手册、去调用链、换模型与无工具配置，产出 195 份报告；完整 Agent 组**故障组件定位 36/39**，根因机制正确 **25/35**（有效评分），保留失败与原始证据。
- **恢复与安全：**用 MySQL 步骤持久化、状态机和租约接续中断任务，通过 **5 类进程中断恢复场景**验证；写操作仅执行人工批准的原单参数，恢复前核对实际状态，以只读账号、token 和费用预算约束访问及开销。
- **后端优化：**以条件更新防超卖，结合 Redis 请求幂等与 Kafka 消费事务去重；采用 singleflight 合并热点查询，同负载对照中回源由 6,295 次降至 400 次，**减少 93.6%**，并通过超时、熔断和降级控制故障传播。

## 可按岗位替换的亮点

- **并发库存：**真实 MySQL 下 100 个并发扣减争抢 50 件库存，50 次成功，余量 0；来源 P1-1、[库存集成测试](../internal/shop/inventory/repository_integration_test.go)。适合替换后端优化一条中的缓存对照，不把两组数据都堆在同一行。
- **系统接入：**诊断服务与状态库独立部署，Loki/OpenSearch 共用日志接口；外部 OpenTelemetry Demo 的五场景各运行工具组和手册组，共十份报告，两组组件定位均为 3/5。来源 P9-25、P9-77、[外部结果](reports/phase-09-formal-results.md)。不宣称已经适配多数生产系统。
- **固定负载测试：**阶段 2 以目标 200 QPS 持续运行五分钟，实际 199.986 QPS、59,998 请求、零错误、P99 51ms。来源 P2-1；条件为单机 Compose 内网、256 工作者、部分热缓存。这是固定负载测量，不是容量上限，因此不作为主文案的核心成果。

## 面试时需要讲清的取舍

说明“为什么选择某种实现”，再用代码与实验支撑：singleflight 的作用范围是单进程同键请求；库存靠条件更新，租约用于诊断执行权；审批时保存参数，恢复时先核对外部状态。不能将工具并发称为多 Agent，也不把专用状态机称作通用工作流框架。

现成组件包括 MCP 官方 Go SDK、gobreaker 和 singleflight；诊断证据、审批策略与场景判分属于项目业务逻辑。模型客户端、结构校验和 Agent 编排尚未与替代框架完成对照选型，不编写已经做过比较的经历。代码入口与已有取舍见[架构](architecture.md)、[设计记录](decisions.md)。

保留的主要失败包括：数据库链路变慢被误判为连接池问题；提示注入材料没有被实际读到，不能声称验证了真实攻击防护；外部系统样本有限；模型评委未经人工校准。写操作仍需人工审批，生产审批人隔离与高可用尚未验证。原始失败见[失败分析](reports/phase-08-failure-analysis.md)与[完整验证记录](demo-and-results.md)。
