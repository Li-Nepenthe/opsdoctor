# 接口变慢时，从请求路径找时间花在哪里

先确定是哪个接口、哪些状态码、多少流量受到影响。总平均值会掩盖少数很慢的请求，也会被流量组成变化影响。把请求量、失败比例和耗时分布放在同一个时间段里看，再决定要检查哪条调用路径。

取几条当前时段的慢调用链。一次调用里的一个步骤叫 span，它有开始时间、结束时间和父步骤。先找耗时最长的子步骤，再比较健康请求的同类步骤。父步骤很慢但子步骤很短时，剩余时间可能花在排队、取连接、序列化或没有埋点的位置，不能把这段空白直接归给下游。

依次区分请求是否到达服务、是否开始访问下游、下游是否实际收到，以及下游内部是否已经完成。发送前等待和发送后的等待需要不同证据。可以用两端的请求计数、错误日志和调用链相互核对。

超时是等待超过预算，不说明远端操作一定失败。写操作结果不确定时，先查业务状态和幂等记录。不要为了证明网络正常而重复提交写请求。只读重试也要检查尝试次数和总时间，避免调查动作进一步增加负担。

修复建议要对应已经证实的耗时位置。调整后用相同流量和同一时间长度复查失败比例、P99 和下游负载。恢复一个指标，不代表所有请求都已经恢复。
