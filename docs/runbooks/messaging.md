# 消息处理排查：把生产、确认和消费分开看

请求成功不代表异步处理已经完成。先画出消息从生产者、消息系统到消费者的路径，再确认用户看到的结果依赖哪一步。分别记录发送次数、发送确认、消费速度、消费错误和积压，避免把“还没消费”误写成“根本没发送”。

积压表示已进入队列、还没有完成消费的消息。积压增长可能是生产更快，也可能是消费更慢或停止。先比较两边的速度，再看消费者进程是否存活、分区是否分配、处理是否卡在数据库或其他依赖上。

发送超时不一定意味着消息没进队列。确认可能晚到，网络也可能只丢了确认。核对消息标识、后续消费记录和业务结果；不要把一次超时直接当作消息丢失。重试必须有去重办法，否则可能重复处理同一件事。

消费者的日志需要与分区、偏移位置和时间对应。偏移位置是队列中的进度标记，不是业务成功的充分证明。程序何时提交进度、业务写入是否已经完成，会影响崩溃后的重复和遗漏。没有相关记录时应保留未知项。

恢复后先观察消费速度是否持续超过生产速度，再看积压能否回落。进程刚启动的一次健康检查不能证明积压已经清空。需要重放消息、修改并发或处理失败数据时，先说明顺序、重复和下游容量风险，由人决定。
