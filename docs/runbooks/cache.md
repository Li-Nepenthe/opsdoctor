# 缓存排查：比较请求、未命中和回源

缓存先替数据库回答常见查询。没找到缓存时再查数据库，这一步叫回源。先对齐商品请求数、缓存命中数、回源次数、数据库查询量和延迟，再判断压力发生在哪一层。只看命中率或只看回源次数都不够。

活跃商品数量越多，同一商品短时间再次被访问的机会可能越少。首次启动、长期停流后的恢复、正常工作集变大，都可能提高未命中率。比较时要记录商品范围、流量、热点分布和缓存过期时间。不能把两个工作集不同的运行直接相减。

缓存不可用与缓存里没有值是两回事。前者需要查看连接错误、超时、内存限制和命令拒绝；后者需要检查哪些键被访问、何时到期，以及数据是否成功写回。只读诊断账号可能不能读取具体值，这时应明确证据缺口，而不是另找权限绕过限制。

多个请求同时查同一个未命中的键时，是否会共用一次回源？大量不同键接近同一时刻过期时，回源是否集中成一阵？用时间曲线和请求之间的关系检查这些假设，不要仅凭一个配置名就宣布根因。回源越昂贵，集中访问造成的后果通常越严重；便宜查询的影响可能很有限。

改进方案可能包括分散过期时间、合并同键查询、限制在途回源、预热或调整工作集。每个方案都有容量和一致性代价。先针对已证实的问题提出建议，再在相同流量下验证，不能为了让曲线好看而悄悄减少请求。
