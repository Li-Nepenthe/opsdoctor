# 数据库排查：先分清在等连接，还是在执行

应用通常复用一组数据库连接，这组连接叫连接池。先看正在使用的连接数、空闲数、等待次数和等待时间。池满只能说明连接不够分；也可能是每条查询占用连接太久。没有查清占用原因之前，扩大池子可能把更多压力送到数据库。

再看数据库当前正在执行什么。把 SQL 的摘要、执行次数、总耗时、扫描行数和返回行数放在一起比较。摘要把参数值去掉，适合把同一类语句归在一起。累计排名要与当前窗口对照，历史执行很多的语句未必是本次原因。

对候选 SELECT 查看执行计划。执行计划说明数据库准备按什么顺序找数据；它不是一次真实运行的耗时证明。核对过滤条件、可用索引、估计行数和表结构。即使用了索引，也可能扫描很多行；全表扫描也不一定昂贵，小表尤其如此。

锁等待需要另一条证据链：谁在等、谁持有锁、持锁事务在做什么、等的是哪类资源。查看状态时保留时刻，事务结束后这份状态就会改变。查询慢、锁等待和连接池等待可以同时出现，必须用先后关系说明它们怎样联系。

还要检查数据库的 CPU、内存、磁盘和重启记录。冷启动后缓存未热、读盘变多，也会使本来正常的 SQL 变慢。提出索引、池大小或事务调整时，写清收益、额外负担、撤销方法与验证步骤；未经审批不执行修改。
